# SC Translator vs ow-translate-lite：深度对比与可优化点

对照源码：`E:\新建文件夹 (6)\ow-translate-lite-master`（.NET 9 / WPF）
本文档对比我们的实现（Python3.12 / PySide6 / RapidOCR / mss）。

## 一、定位差异（根本不同，决定后续取舍）

| | ow-translate-lite | SC Translator（本项目） |
| --- | --- | --- |
| 场景 | 只做《守望先锋》外服**聊天**翻译 | 通用：任意框选区域实时翻译（聊天/任务/商店/帮助） |
| 解析层 | 有：OW 聊天解析器（识别 `[玩家]: 正文`、过滤系统/频道噪音、术语表替换） | 无（曾做过 SC 聊天模板，按你的要求移除；纯区域 OCR 逐行镜像） |
| 消息身份 | 时间线 Timeline + Seq 对齐：按“消息身份”去重/排序/滚动恢复 | 按屏幕行锚点 + 文本内容；无“同句两人不同”区分，无滚动历史恢复 |
| 数据规模 | 单区域聊天窗（小图、纯文本） | 区域任意，可能含大图/UI |

这个差异是理解下文“为什么它敢高频、我们要节流”的前提：
它只在**小面积纯文本聊天框**上工作，OCR 每帧便宜，所以可以用 300ms 高频；
我们面向任意区域（可能很大），一次 Paddle OCR 在 471×268 上也要 ~0.5-0.75s。

## 二、抓屏与变化检测

- 两者都是 GDI BitBlt（ref 用 Graphics.CopyFromScreen；我们用 mss→BGR），**独占全屏都抓不到**，须窗口化/无边框。
- ref：**每 250~300ms 固定抓一次**，做“每 8 像素采 1 点亮度”的签名比对（C# 极廉价），变化才允许 OCR。
- 我们：静止时 1.5s 抓一次 + OpenCV 缩略签名（96px 宽）；变化时 200ms 抓。
  结论：**空闲开销我们更低**；ref 只是“每次都很便宜”，不是“更闲”。
- 我们额外做了逻辑/物理坐标与 DPI 换算、跨屏处理（ref 用 ScreenBoundsService 换算，思路一致）。

## 三、OCR 引擎与预处理（CPU/质量差异的核心）

| | ref (OneOCR) | 我们 (RapidOCR) |
| --- | --- | --- |
| 引擎 | OneOCR 原生库（行级），单核友好、快 | PaddleOCR onnx（det+cls+rec），可多线程但会严重超卖 |
| 预处理 | 先 **2× 双三次放大 + 轻度锐化 + 对比度1.18/gamma0.96** 再识别，框回映射回原坐标（为“小字号字体”提升召回） | 无预处理，直接识别原图 |
| 后处理 | Trim、去空行 | NFKC、去重框、视觉行聚类、camelCase/数字边界补空格启发式 |
| 线程 | 单核/内部可控 | 已限 onnx 单线程 + 进程绑单核(优先小核) |

发现与已做优化：onnx 在“线程=2”时实际吃掉 ~3.4 核（超卖），改单线程后降到 ~1 核；
另把整个进程钉在单逻辑核（混合 CPU 优先 E-core），避免后台 OCR 抢游戏的大核。

## 四、调度策略对比（最重要的一页）

ref 的调度（MainWindow.RunLoopAsync + UpdateOcrSchedulerAfterOcr）：
```
每 250-300ms: 抓屏 + 廉价签名比对
  ├─ 无变化 → 什么都不做（不 OCR）
  └─ 有变化 且 距上次探测已过:
       空闲态探测间隔 700ms → 或活跃窗内 300ms
       进入突发：burst=3 帧
       若连续看到聊天 → 进入 5s“活跃窗”，可 300ms 连拍
       连续 2 次 OCR 无聊天 → 退回空闲
OCR 全程被 Semaphore 互斥（单实例识别）；翻译入队后异步批量发 API
```
ref 的取舍：**小区域 + 便宜引擎 → 高频突发但单帧便宜**；翻译队列把网络延迟与 OCR 解耦。

我们的调度：OCR 间隔固定 ≥3s（可变设置），变化后最多补跑 2 次确认；静止 1.5s 巡检。
优势：空闲更省、最坏 CPU 低；
劣势：**没有“活跃窗/两档节奏”**——聊天频繁时也最多 3s 一次，响应偏钝；没有“连续无文字就加大退避”的闭环。

## 五、消息确认/去重模型

| | ref | 我们 |
| --- | --- | --- |
| 观察确认 | 每条消息多次可见(SeenCount)才入队翻译 | 行文本连续 2 帧稳定才提交 |
| 重复 | Timeline 身份匹配 + OCR 归一化相似度，滚动历史重开不重译 | 同锚点+同文本原地更新；同文本不同人会被合并 |
| 滚出区域 | 保留在 Timeline/overlay 历史中（可回滚） | 行消失即从悬浮框移除（无历史） |
| 失败 | 状态机（Confirming→Queued→Translating→Translated/Failed），失败≤2次重试 | 失败标记 + 20s 节流重试（请求级） |

## 六、翻译请求与队列

- ref：翻译**批量**发送（≤4 行/批，溢出批 30 行），队列上限软30/硬100，串行批量降低 API 次数与延迟；有术语表注入、最近聊天语言自动判断源语言。
- 我们：**逐行单请求**、单一串行 worker；同文合并 + 磁盘缓存 + 失败节流。
  可优化：把一轮新行**合并成一个批量请求**（编号行列表一次返回），显著减少请求次数/网络往返；缓存层面我们已分开 normal/spicy，另有输入输出交换日志（ref 无）。

## 七、健壮性/诊断/工程

- 都有 DPAPI 密钥、深浅主题、日志。
- 我们有：启动/崩溃日志、输入输出交换日志、提示词外置 md（可编辑）、便携 data 目录、区域OCR自检、单核绑定、空内容护栏、跨DPI 换算。
- ref 有：全局热键（回话翻译、手动 OCR Ctrl+Shift+T）、自动更新/卸载器、反馈包导出、设置迁移、诊断开关、术语表校验工具；overlay 顺序按 Seq 回填（乱序不抖动）。

## 八、可优化点（按价值排序）

1. **两档调度（活跃/空闲）+ 无文字退避**（高价值、中低改动）
   复刻 ref 思路：识别到可见行/持续变化 → “活跃”用较短的 OCR 间隔（如 1.2s）；连续几次无文字 → 退回 4~6s 长间隔。比固定 3s 更跟手，空闲更省。
2. **翻译批量合并请求**（高价值、中等改动）
   一轮确认的若干行打包一次 `/chat/completions`（多行编号返回），减少请求频率与总体时延，特别适合聊天连发。
3. **文本存在预判门（可选，默认开）**（中价值、中等改动）
   在 96px 签名图上做廉价“类字形像素”统计，明显无文字的“变化”（鼠标、背景晃动）直接跳过 OCR。参考仓库里有 TextPresenceGate 但正式循环并未启用，说明它有误伤风险——我们会做成默认开但可关、阈值放宽。
4. **全局热键**（中价值、低改动）
   RegisterHotKey：如 `Ctrl+Shift+T` 手动对当前区域识别一次、一个热键切“固定/穿透/显示隐藏”，方便游戏内操作。
5. **滚动历史/两人同句去重增强**（仅聊天场景需要；我们通用模式可不做）
   如需聊天增强：加“最近消息表”按文本+时间短窗口去重，重叠行保留末尾。
6. **包体与分发**（远期）
   PyInstaller 打包成单个 exe/便携 zip + 自动更新（当前以源码+venv 运行）。
7. **预处理增益开关（可选）**
   对偏小字体或 SC 界面可先轻度对比度/CLAHE 增强再识别；会增加少量 CPU，做成“低质量区域增强”选项。

## 结论

我们与 ref 的差距主要在：**解析层（场景差异）、调度两档节奏、批量翻译、热键**；
性能差距已通过“onnx 单线程 + 单核绑定 + 3s 间隔 + 静止慢巡检”拉平甚至更省。
下一步最值得做 1+2（调度两档 + 批量翻译），既能降请求频率又提升活跃时的跟手度。
