### 1.7 单实例锁附加验证（复核项 7，报告第 5 节附加项）

我用**真正的 `QLockFile`** 造锁（而非文本文件），在临时 home 下启动被测程序，分三种场景：

| 场景 | 造锁方式 | 观察结果 |
|---|---|---|
| A 无锁 | 不造锁 | 退出码 0，4.48s，无残留 ✅ |
| B 持有者进程已死（未回拨） | 子进程持锁后被强杀 | **退出码 0，4.47s**，无残留 → 自动接管 ✅ |
| C 持有者进程已死 + 回拨 30s | 同上 + 回拨 | **退出码 0，4.51s**，无残留 ✅ |
| D 持有者**仍在运行** + 回拨 30s | 活进程持锁 + `os.utime` 回拨 30s | **停在弹窗，25s 超时未退出**，lock 残留 ❌ |
| E 持有者仍在运行（新鲜） | 活进程持锁 | 停在弹窗，25s 超时未退出 ❌ |

补充：用**纯文本**写一个 `instance.lock`（非 QLockFile 格式）时，程序会当作损坏锁直接接管并正常退出
（首次尝试即被此行为误导，故改用真锁复测）。

结论见 **F-02**：`QLockFile.setStaleLockTime(15_000)` 的接管条件不只是「文件时间超过 15 秒」，
还取决于锁内记录的**持有者进程是否存活**。报告把「30 秒前的陈旧锁自动接管」作为独立结论呈现，
但既未说明造锁方式，也未区分死/活进程；我实测「回拨 30s + 活进程」**并不接管**，与该表述不符。

### F-02（medium）「陈旧锁 30 秒自动接管」的附加验证证据不足且表述与实测不符

- **问题**：报告 §5 附加验证称「预置一个 **30 秒前的陈旧锁** 时程序正常启动并在 4.58s 后退出码 0 —— 
  即 15 秒陈旧锁自动接管逻辑生效」。但未说明该锁文件的**造锁方式**。`QLockFile` 的接管判定
  不只是文件时间，还取决于锁内记录的持有者进程是否存活（`setStaleLockTime(15_000)`）。
- **我的实测**（真 `QLockFile` 造锁，临时 home）：

  | 场景 | 结果 |
  |---|---|
  | 持有者进程已死 + 回拨 30s | 退出码 0，自动接管 ✅（与报告结论一致） |
  | 持有者**仍在运行** + 回拨 30s | **停在弹窗，25s 超时未退出** ❌（与报告表述相反） |
  | 持有者仍在运行（新鲜） | 停在弹窗，25s 超时未退出 ❌ |

  即报告举证的「30 秒前」这一时间条件**本身并不足以**产生接管；真正起作用的是持有者进程死亡。
  报告未披露关键前提，读者据其表述可能误判「时间到点就会自动接管」。
- **实测中还发现一个易误导的现象**：手工写入**纯文本** `instance.lock` 时，`QLockFile` 视其为损坏锁并
  **直接接管并正常启动**（我第一轮验证即被此现象误导）。这会让任何用文本文件模拟"陈旧锁"的验证得到假阳性。
- **要求修复**：在 §5 附加验证中写明造锁方式与持有者进程状态，并区分「死进程接管（成立）」与
  「活进程 + 时间回拨（不接管）」两种情形；或将该附加项从结论区移入"未充分验证"并标注。
  注意该附加项为**非必做项**，不影响主流程判定。

### F-03（low）「测试后 `data\cache.json` 未改动」不准确

- **问题**：报告 §4.2/§7 称测试后 `data\cache.json` 未改动（mtime 保持 2026-09-10）。
  实测：`data\cache.json` 的 mtime 为 **2026-09-12 14:22:12**，`settings.json` / `api_key.bin` 保持
  2026-09-10 14:58:03 不变。
- **归因（已定位，非报告作者之外的问题）**：冒烟运行本身会改写该文件 ——
  `app.shutdown()` 调用 `self.cache.flush()`（`app.py:445`），`flush()` 用内存快照**整体重写** `cache.json`
  （`translate/cache.py:62-69`）。实测：冒烟前 mtime `14:22:12` → 冒烟后 `14:27:52`，**内容字节数不变（6685 B）**。
- **严重度说明**：内容未被污染（文件仍为 6685 B，未写入本次真实译文；我另外 grep 确认真实
  `data\cache.json` 中 **不含** `派罗星系` / `Heading to` / `Verse`）。属"精度/措辞"问题而非功能缺陷。
- **要求修复**：把该表述改为按内容断言，例如「`data\cache.json` 内容未被测试写入（字节数与键集不变，
  仅被冒烟启动的 `cache.flush()` 刷新 mtime）」，或改为「`settings.json`/`api_key.bin` mtime 未变」。
