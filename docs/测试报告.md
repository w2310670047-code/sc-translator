**不使用文本文件冒充陈旧锁** —— 手工写纯文本 `instance.lock` 会被 `QLockFile` 视为**损坏锁并直接接管**，
从而产生假阳性（复核者第一轮即被此现象误导，`docs\复核报告.md` F-02 已指出）。
**持有者进程状态**：由脚本记录每个持有者的 PID 与 kill 前后的 `poll()` 值。
**对话框处理**：offscreen 下 `QMessageBox.information` 会永久阻塞，故子进程内 patch 该静态方法为记录器，
从而拿到**确定的退出码**（不再依赖「25s 超时」这一不稳定现象）。

**命令**

```powershell
cd "E:\SC Translator"
$env:QT_QPA_PLATFORM="offscreen"; $env:PYTHONIOENCODING="utf-8"
.\.venv\Scripts\python.exe "tools\复核-单实例锁.py"
```

**关键输出**

```
[A 无锁（基线）] 退出码 = 0（期望 0）OK；耗时 3.44s；提示框被触发 = False
[B 造锁] 真 QLockFile 由子进程持有(pid=28072, 强杀前存活=True)，随后 kill → 持有者进程已死
[B 持有者进程已死（未回拨）] 退出码 = 0（期望 0）OK；耗时 3.45s；提示框被触发 = False
[C 造锁] 同上，并对 instance.lock 回拨 30s（mtime=14:29:27）
[C 持有者进程已死 + 回拨 30s] 退出码 = 0（期望 0）OK；耗时 3.44s；提示框被触发 = False
[E 造锁] 子进程 pid=20968 持有新鲜锁且**仍在运行**（poll=None）
[E 持有者存活 + 新鲜锁] 退出码 = 1（期望 1）OK；耗时 0.20s；提示框被触发 = True
[D 造锁] 子进程 pid=30340 持有锁且**仍在运行**，锁文件回拨 30s（mtime=14:29:31）
[D 持有者存活 + 回拨 30s] 退出码 = 1（期望 1）OK；耗时 0.21s；提示框被触发 = True
清理：instance.lock 残留 = False
==== 单实例锁复核汇总：全部符合预期 ====
EXIT=0
```

| 场景 | 造锁方式 | 持有者进程状态 | 实测结果 | 判定 |
|---|---|---|---|---|
| A 无锁 | 不造锁 | — | 退出码 0、3.44s、无 marker/lock 残留 | 正常启动 |
| B 持有者已死（未回拨） | 真 `QLockFile`，子进程持锁后被 kill | `poll()` 已结束 | 退出码 0、3.45s、提示框未触发 | **接管成立** |
| C 持有者已死 + 回拨 30s | 同 B，另对 lock 文件 `os.utime` 回拨 30s | `poll()` 已结束 | 退出码 0、3.44s、提示框未触发 | **接管成立** |
| E 持有者存活（新鲜锁） | 真 `QLockFile`，子进程持续持有 | `poll()=None`（存活） | **退出码 1**、0.20s、提示框被触发 | **拒绝启动** |
| D 持有者存活 + 回拨 30s | 同 E，另把 lock 文件回拨 30s | `poll()=None`（存活） | **退出码 1**、0.21s、提示框被触发 | **拒绝启动（时间回拨不构成陈旧）** |

**修正后的结论**：
1. 「持有者进程已死 → 接管」**成立**（B、C 两场景，含时间回拨）；
2. 「持有者进程存活 + 时间回拨 30s → **不**接管」**成立**（D 场景，退出码 1），
   即接管判定取决于锁内记录的**持有者进程是否存活**，而非单纯的文件时间；
3. 被拒绝时程序以退出码 1 结束（`__main__._run()` 在提示后 `return 1`），且不写 `app_ready.marker`。

第 1 轮报告中「预置纯文本 lock 后 30s 自动接管」的旧描述**已作废**（那其实是 QLockFile 把损坏锁当废弃处理，
不能证明陈旧锁接管逻辑）。

**证据**：`%TEMP%\qa_smoke.out`（冒烟）、`%TEMP%\qa_lock.out`（锁四场景）、
`%TEMP%\qa_double_start.out`（第一轮未修订的旧场景，仅作对照）。

## 8. 发现的问题（均不阻断，建议后续修复）

**F1（低）单测污染真实交换日志**
`tests/` 中未使用 `tmp_home` 的用例（如 `test_translate.py`）会调用 `OpenAiCompatClient.translate_line`，
其内部 `exchange_log.record(...)` 使用全局 logger 并落到**真实** `data\logs\exchange.log`。
实测两次 `pytest` 各向该文件写入 16 条合成记录（`model=m` / `deepseek-chat`、含 `HTTP 500: {}` 假错误），
使真实运行日志与测试数据混杂（文件有 2MB 轮转，长期风险有限）。
复现：`pytest tests -q` 两次 → `data\logs\exchange.log` 尾部出现 `model=m style=spicy` 等假记录。
实际结果：真实日志被写入 32 条测试数据。
建议：在 `tests/conftest.py` 加 autouse fixture（`exchange_log.reset()` + 指向 `tmp_path`）或在 `_chat` 错误路径统一注入。

**F2（中）嘴臭回话在交换日志中被记为 `style=normal`**
`translate/client.py:366,368` 的 `translate_reply()` 记录时硬编码 `style="normal"`，
未按 `spicy` 参数写 `style="spicy"`。离屏嘴臭回话（`spicy=True`）在 exchange.log 中呈现为
`[kind=reply ... style=normal ...]`，与正常回话无法区分，削弱了口径核对能力（缓存与提示词本身是正确的：
嘴臭走独立提示词、不落缓存、`_cache_model()` 对 realtime 路径会追加 `#spicy`）。
复现：见第 6.2 节最后一条记录（输入 `别跑啊，单挑`，实际由 `spicy=True` 产生）。
建议：`style="spicy" if spicy else "normal"`。

**F3（低）术语表预替换会留下英文残片**
自动挖掘出的长词条缺失时，短词条会先命中，导致句中仍留英文：
`glossary.apply('Pyro System is dangerous') -> '派罗星系 is dangerous'`（`Pyro System` 未收录为长词条）。
虽然模型通常能补全成「派罗星系很危险」，但预替换层本身产生中英夹杂输入。
复现：第 4.1 节命令最后几行。
建议：术语表补 `Pyro System = 派罗星系` 一类“专名+System/Station”长词条，或在替换后清理孤立 `System/Station`。

**F4（低）日志噪音**
- 启动/退出各写两条 `应用退出`（`app.shutdown()` 与 `__main__` 的 finally 路径重复），同一秒重复行易误判；
- offscreen 平台插件固定输出 `QFontDatabase: Cannot find font directory` 与 `propagateSizeHints` 提示；
- 无真实缺陷，仅建议去重与降噪（例如给 shutdown 加幂等标志）。
